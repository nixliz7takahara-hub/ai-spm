## 1. 監査で見つかった欠陥(優先順・再現済みは実測ログ付き)

### 🔴 1-1. 判定エラー時が無自覚フェイルオープン

`layer2.judge_real` がエラーを返すと `risk="unknown"` → `RISK_RANK` で 0 → **allow / verdict=benign / layer="cascade"** になる。実測:

```
{"decision": "allow", "verdict": "benign", "layer": "cascade",
 "reason": "[error] RateLimitError: 429", "risk": "unknown", "error": true, "cost_usd": 0.0}
```

- 429(レート制限)はバーストを打てば攻撃者が**無料で**起こせる。起きている間は第1層を通過した全入力が allow。
- 判断1の降格は「予算枯渇」だけを想定して意図的に設計したが、**エラー経路は同じ結果を"cascade / benign"という嘘のラベルで出している**。評価ハーネスで一度踏んだ「APIエラーを握り潰すと失敗が benign 改善に化ける」の本番版。
- 非対称: Haiku=low → Sonnet エラー のときは Haiku の low が残って block(保守的)。Haiku エラーのときは allow。これは一貫性がない。

**直し方**:
- Haiku がエラーなら **Sonnet を1回だけ試す**(ユーザ判断②・既定は試す)。
- 両方エラー、または Haiku エラーで Sonnet を試さない設定なら、`layer="judge-error"`, `verdict=None`, `degraded=True` で返す(予算降格と同じ意味=「判定していない」)。`METRICS["degraded"]` にも数える。
- `risk="unknown"` を block/allow の計算に**絶対に入れない**(今は rank 0 として allow 側に倒れている)。

### 🔴 1-2. スコープガードが正規化**前**のテキストに走る

`_scope_violation(text)` は生テキスト、第1層は NFKC 後。実測:

```
全角 base64 2,400字(ＱＵＪＤ…): 生テキストでは違反なし → NFKC後は ASCII 2,400字の塊 = 本来 reject
"ﬃ" × 7,900字: 生 7,900字で通過 → NFKC後 23,700字 が判定モデルへ(長さ上限の3倍)
```

- 入力長上限の目的(1リクエスト最大コストの上限)が破れる。8,000字なら Sonnet 込みで ≈$0.007/req が上限のはずが、3倍まで膨らむ。
- base64 塊上限は全角で素通り(第1層の decoder は NFKC 後に動くので、2,000字超の塊が decode される)。

**直し方**: `norm = layer1.normalize(text)` を先に取り、`_scope_violation(norm)` を見る。長さは**生と正規化後の両方**を上限にかける(生で弾けば NFKC の計算すら不要)。`layer1.inspect` は正規化済みを受け取れるようにするか、2回 normalize する(冪等・安価)。

### 🟠 1-3. 予算状態ファイルにロックが無く、並列実行は**今すでに**起きる

`app.py` の `/check` は `def`(同期)なので Starlette が **threadpool で並列実行**する(`starlette/routing.py` の `run_in_threadpool`・anyio 既定の上限 40 スレッド)。ブリーフの「同期」は誤認。

- `can_spend()` → API 呼び出し(数秒)→ `record()` の間に別スレッドが何本でも `can_spend()` を通る。**オーバーランは「1リクエスト分」でなく「並列数 × 1リクエスト最大コスト」**。40 × $0.007 ≈ **$0.28**(日次 cap $1 の 28%)。
- `_load()` → 加算 → `_save()` に排他が無い。2スレッドが同じ状態を読み、各自の分だけ足して書く = **ロスト更新で過少計上**。cap が効かなくなる方向の誤り。
- `METRICS` の `+=` も同じ(こちらは監視値なので実害は小)。

**直し方**: §4 参照(`threading.Lock` + 判定経路の `Semaphore`)。

### 🟠 1-4. Anthropic クライアントを呼び出しごとに生成している

`layer2.judge_real` は毎回 `Anthropic()` を作る。TLS ハンドシェイクと接続確立が**1リクエストで2回**(Haiku+Sonnet)入る。「約6秒」の内訳を測る前に async を決めてはいけない。

**直し方**: モジュールレベルで1つ作って使い回す(`anthropic` クライアントはスレッドセーフ・接続プール内蔵)。その上で `latency_ms` を Haiku/Sonnet 別に出して再計測。

### 🟡 1-5. 降格時の `verdict="benign"` は不誠実なラベル

判定していないものを "benign" と呼んでいる。`degraded=true` で区別はつくが、下流が `verdict` だけ見れば「判定済み無害」と誤読する。**`verdict=None`**(reject と同じ扱い)にする。1-1 の judge-error も同じ形に揃える。

あわせて `/health` は**降格中は `status: "degraded"`** を返す(今は常に "ok")。これだけで外形監視が拾える=§8-2「降格の通知」の最小形。入出時に `{"event":"degraded_enter"|"degraded_exit"}` を1行ログに出す。

### 🟡 1-6. HTTP 層で入力長が無制限

`CheckIn.input: str` に `max_length` が無い。巨大ボディを**全部パースしてから** 8,000字判定に入る。`Field(max_length=MAX_INPUT_CHARS)` を付ける(生の長さ上限はここに一本化してよい。1-2 の生側チェックと兼ねる)。

### 🟡 1-7. テストが 0 本

4経路の検証は手動ログのみ。`layer2.judge_real` を差し替えれば **API 無しで全経路が回る**(本監査の再現スクリプトがそのまま雛形)。`tests/test_gateway.py`(pytest)に:
- scope reject(生/正規化後の両方・全角 base64)
- layer1 block
- 予算降格(allow・verdict None・degraded・/health degraded)
- カスケード(Haiku none → allow / Haiku low → Sonnet 呼ばれる → Sonnet の判定が勝つ / Sonnet エラー → Haiku 判定が残る)
- **judge-error**(Haiku エラー → Sonnet 試行 → 両エラーで judge-error・allow 側に倒れないこと)
- 予算 record の並列加算(10スレッドで合計が一致)

### 🟢 1-8. ログに入力の識別子が無い

本文を残さないのは正しい(PII)。ただし判定の事後監査ができない。**正規化テキストの sha256 先頭16字**を `input_hash` として出す。1-3 の重複率計測(§5)にも使う。

### 🟢 1-9. `budget_state.json` の日キーが無限に増える

実害は年単位で先。`record()` 時に 60 日より古い日キーと 13 か月より古い月キーを落とすだけでよい。

### 🟢 1-10. URL-safe base64(`-` `_`)は scope も第1層 decoder も素通り(記録のみ)

`[A-Za-z0-9+/]` のみ対象。URL-safe 変種は decode されずに判定モデルへそのまま届く。**評価数値に含まれる既知の限界**として README/CASE_STUDY §10 に1行追記。B1 の対象外(第1層の改修は評価数値の再計測を伴う)。

## 3. 「キャッシュ無し」の根拠の書き換え

「同一入力の再判定で攻撃者に安定した探索オラクルを与えない」は弱い。キャッシュ無しでも攻撃者は毎回**新鮮な判定**を得る(ノイズが乗るだけでオラクルはオラクル)。探索対策の本丸は**クライアント別レート制限**であり、それにはクライアント識別が要る(§5 ユーザ判断①)。

キャッシュ無しの**強い理由**は2つ: (1) 判定の鮮度(モデル・プロンプト更新が即反映)、(2) キャッシュキーが "攻撃が通った入力" の索引になる保管リスク。README とコメントはこの2つに書き換え、「オラクル」は副次に落とす。

## 4. §8-1 ソフトキャップ: 許容、ただし2条件

ハード予約(事前見積りで枠を取り、事後に精算)は $1/日 の規模では過剰。ソフトのままでよいが、**1-3 を直さない限り「ソフトキャップ」ではなく「キャップ無し」**である。条件:

1. `service_budget` に `threading.Lock` を1つ置き、`record()` の load→加算→save を原子化。`status()`/`can_spend()` も同じロックで読む(短い)。
2. 判定経路(`_cascade_live` 呼び出し)に **`threading.Semaphore(AISPM_JUDGE_CONCURRENCY=8)`**。これで**オーバーラン上限 = 8 × $0.007 ≈ $0.06** と数字で言える。README に「cap は soft。超過上限は並列数×1リクエスト最大コスト = 既定 ≈$0.06」と書く。
3. `can_spend()` と `record()` を1つのトランザクションにする必要は**ない**(それがハード化で、やらないと決めた)。

## 5. 次増分の優先: C → B → (A は保留)

### なぜ A(async/streaming)を今やらないか
- **需要が無い**: $1/日 = 500判定/日 = 3分に1件。スループットは問題ではない。
- **6秒の内訳が未測定**: 1-4(クライアント生成)を除いて Haiku/Sonnet 別に計ってから。
- **streaming はこの用途に無効**: ツール呼び出しの JSON 判定は全部届くまで決められない。体感も変わらない。
- このプロジェクトの価値は「計測の誠実さ」(CASE_STUDY の芯)。**1-1 を残したまま async に進む**のは、本番の判定結果に「失敗が benign に化ける」を仕込むことになる。

### C(本監査の修正・半日・$0)の受け入れ条件
1-1 〜 1-9 を実装。**1-7 のテストが全部緑**であること。API 呼び出しは不要(差し替えで回す)。最後に実カスケードを2件だけ再実行(≈$0.005)して `latency_ms` の Haiku/Sonnet 内訳を取る。

### B(監視詰め・判断3)の受け入れ条件(C の次)
目的は「医師の診断」ではなく**「見に行く合図」**。完璧な区別は不可能で、それを目指すと家具になる。

1. **スライディング窓のエスカレ率**: 直近 N=100 判定(`collections.deque`)。基準 20%・**35% 超で `{"event":"escalation_alert"}` を1行ログ**。`/metrics` に `escalation_rate_window` を追加。
2. **区別のための3指標**(`/metrics` に出すだけ・判定はしない):
   - エスカレされた入力の **Sonnet 最終判定の分布**(`none` 率が高い=無害側の分布変化 / `attack` 率が高い=攻撃増)
   - **クライアント別**のエスカレ件数(要クライアント識別=ユーザ判断①)
   - `input_hash` の**重複率**(同一入力の連打=探索。1-8 が前提)
3. 降格の出入りイベント(1-5 で済み)。
4. B の検証もモック差し替えで $0。実 API は最後の疎通 2 件のみ。

### ユーザ判断(現場からユーザへ上げる2点)
- **① クライアント識別を今入れるか**: `X-Client-Id` ヘッダ1本(認証ではない・無ければ "anonymous")。レート制限と per-client 監視の前提。**推奨=入れる**(後から入れると監視値が遡れない)。
- **② Haiku エラー時に Sonnet へフォールバックするか**: 単価 20 倍だがエラーは稀。**推奨=1回だけ試す**。両方エラーで judge-error 降格。
